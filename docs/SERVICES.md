# 服务与算力

## 谁在运行

| 设备 | 服务名称 | 作用 |
| --- | --- | --- |
| A | `starport-console` | 会话、消息缓存、附件和成品 |
| A | `starport-panel` | 管理面板与使用指南 |
| B | `starship` | Claude 会话与后台执行 |
| B | `starship-activity` | 当前处理状态 |
| B | `starship-model-settings` | 模型与 effort 设置 |
| B | `starship-auth` | 账号状态检查 |

Linux 使用同名 `.service`；macOS 使用 `io.starport.` 前缀的 launchd 服务；
Windows 使用任务计划中的 `Starport` 文件夹。

```sh
# A：看实际注册
python3 starport.py services

# B：检查客户端
python3 starship.py status
```

**运行、登录启动、重启验收是三件事。** 用户服务默认随登录启动，锁屏保持运行。
手动模式和取消注册见[维护指南](MAINTENANCE.md)。

## 面板可以管理什么

新安装先提供会话工作台。连接旧工具包后，面板还能显示其 SMB、VNC、监控、路由和训练服务。
只有固定允许的服务提供操作按钮；发现一个服务不等于获得重启它的权限。
路由、隔离守卫和训练核心保持只读，按各自维护流程更新。

## 接入已有计算节点

```text
A 的调度入口 → 受限连接 → 远端执行器 → 任务专属文件 + 只读依赖／数据
```

当前算力适配层接入**已有 Linux 隔离执行器**。它不自动创建云实例、安装完整训练环境或挂载共享卷。
先准备节点注册表、任务状态目录、每节点配置和健康／暂停／恢复接口，再复制示例配置到仓库外：

```sh
python3 -m isolation_toolkit.compute_sync --config ../config/compute-sync.json --install
```

示例：[compute-sync.example.json](../examples/compute-sync.example.json)。
节点账号、SSH 路径和资源上限由操作端填写，B 只使用对外的节点名称和任务接口。

## 状态如何自动恢复

| 情况 | 行为 |
| --- | --- |
| 节点失联／代理出口失效 | 暂停该节点接收新任务，保留已有任务和预留 |
| 连接恢复 | 连续检查通过后恢复；不会覆盖人工暂停 |
| 实例规格改变 | 同步 GPU、CPU、内存，保留系统余量 |
| 状态过期 | 不再当成可提交容量；监控仍显示节点及最后检查时间 |
| 遗留预留 | 只有清理、进程和资源锁证据都确认后才释放 |
| 有未收回的完整结果包 | 等待回收，不直接改成失败并删除 |

默认每 30 秒检查；120 秒未更新视为过期。代理 HTTPS 在 12 秒内最多尝试三次，
始终经过原代理并校验证书。新接收进程只在空闲后替换旧进程。

## 断线时训练会怎样

支持 `control_mode: durable-task-v1` 的专用单节点任务由远端监督进程托管：
控制端断线后继续运行，恢复后按原任务 ID 接管，不重复训练。

| 数据 | 恢复方式 |
| --- | --- |
| 日志 | 16 MiB 近期游标缓冲，加有上限的压缩分段；缺口明确提示 |
| 结果 | 保存在远端，支持续传和摘要校验 |
| 资源 | 远端完成并确认清理后释放，不必等控制端上线 |
| 连接提示 | 恢复成功后清除旧提示；重连次数保留为本次控制进程内的历史记录 |

取消、训练期限、内存限制和执行器故障仍然有效。服务器重启后的训练恢复依赖应用的 checkpoint。
标准队列、跨服务器任务和旧执行器不自动获得该能力。
详细接入约定见 [compute_runtime](../compute_runtime/README.md)。

## 容量怎么看

`ready` 是节点可用，`accepting_new_jobs` 是是否接收新任务。预留量是已分配额度，利用率是当前忙碌程度。
GPU 空闲仍可能受 CPU、内存、资源锁或手动暂停限制。先看拒绝原因，不要直接取消其他任务。
